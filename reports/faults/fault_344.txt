Why this is the fault.
The Javadoc spells out the semantics:
  1234     -> 1234
  a        -> 0
  1234a123 -> 123          (the LAST integer)

The buggy code returns the FIRST digit run as soon as it sees a
non-digit. Failing tests I traced:

  extractIntInStr("0366-01-31") expected 31  got 366
  extractIntInStr("52 Saaaaaa") expected 0   got 52
  extractIntInStr("10th")       expected 0   got 10
  extractIntInStr("1 S")        expected 0   got 1

With my patch, the accumulator resets to 0 on every non-digit and the
final `return num;` on line 349 yields the last digit run. That
matches all failing tests and the passing case "1234" -> 1234 (no
non-digit, no reset).
